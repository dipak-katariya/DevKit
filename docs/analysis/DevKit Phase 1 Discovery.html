Plan check

Gaps in the plan itself, raised before the work as the brief asks.

  1. The template's placeholders are empty. Repo, stack and API stability were not filled in. I assumed DevKit at the path above, C# on .NET 10 Blazor Server, and no breaking changes to its external contracts (listed below). Confirm in Q1.
  2. Its structure rules contradict your own standards. "One public type per file", "class ≤ 400 lines", "method ≤ 60 lines" and "no Helper/Util/Common" clash with your global rules: no 30–80-line fragment files, files up to about 500 lines, methods ≤ 40–50 lines, shared code in Common/<Area>. One of them has to win (Q2).
  3. The database items don't apply. DevKit has no database; its data comes from TFS REST calls, local git and one settings file. I read "DB calls in loops", paging and timeouts as TFS requests in loops, paging and timeouts.
  4. The definition of done needs tooling that doesn't exist yet. There is no CI pipeline, no SonarQube project, no coverage collector in DevKit.Tests, and no component-test library. M0 has to add these, which means new dependencies and a SonarQube server or token from you (Q4).
  5. Most uncovered flows are page logic that no current test can reach. 90 of 146 flows have no test, and most of their logic lives in Blazor pages. Pinning them needs bUnit or browser tests against fake TFS. Without one of those, many hit your own stop condition "a flow has no feasible test".
  6. Golden outputs from live TFS would put internal data in the repo. Real work-item titles, names and branch names would end up in golden files. I propose building golden inputs from the fake-TFS handlers the tests already use (Q5).
  7. "Open source" may not be true yet. The code carries Casepoint-specific values: the internal TFS host in a placeholder (Settings.razor:18), custom fields Casepoint.TFS.CustomFields.* (TfsApiService.Audit.cs:280,285, TfsApiService.Capacity.cs:166, TfsApiService.WorkItems.cs:218), a hardcoded team list (TfsApiService.cs:24-27) and the sidebar label (MainLayout.razor:12). If DevKit is going public, these become findings (Q3).
  8. Rollback by commit is workable now. The branch was committed and pushed as f9bc06f and origin/main includes it (PR #2), so each milestone can be one revertable commit.
  9. A stop condition was already hit. Discovery turned up 139 behaviours that look like bugs. Under your rules I halted rather than fix them; they are listed below for triage (Q7).

      What I assumed or need from you before Phase 2.

      2. Which size and structure rules win? The template's (one public type per file, class ≤ 400, method ≤ 60, no Common folders) or your global ones (no small fragment files, ~500-line files, methods ≤ 40–50, Common/<Area>)? I'd take the stricter number for each size limit, and colocate small records and enums with their owner rather than give each its own file.
      3. Is DevKit going open source? If yes, the Casepoint-specific values named in the plan check become findings to move into settings.
      4. May M0 add tooling? That means coverlet.collector for coverage, bUnit (or Playwright) for page-level characterization tests, a CI workflow (GitHub Actions, since the remote is GitHub) and a SonarQube or SonarCloud project. I need the SonarQube server and project key, and a token you set yourself.
      5. Golden outputs. May I build them only from the fake-TFS handlers the tests already use, never from live TFS data?
      6. uzera. Nothing in the code references it, so there is nothing to remove from the application. The options are: delete the 1,606 git-ignored .remember logs that mention it through PATH dumps; keep or reword the two documentation lines; keep the .claude block (my recommendation). Do you also want the machine-level check of the global Claude hooks and the wrapper that I skipped at your request?
      7. Bug triage. May Phase 2 verify the 23 raise-first items before anything else, each one logged as its own fix task outside the refactor? One is a design choice only you can make: MergeRollup.cs:95-99 lets a work item read "Merged" while one of its pull requests is still active or unchecked. I confirmed in the code that this is by design ("unchecked PRs don't drag a work item down"), but it conflicts with your rule that a false "merged" is the worst outcome.
