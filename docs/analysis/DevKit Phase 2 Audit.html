      Act now: exposure on this machine today

      These are confirmed and reachable in normal use. Under your rules nothing gets fixed before you approve the plan, so they wait for your decision (D1). Until then, keep DevKit stopped when you are not using it, and don't use the Merge Tool on a clone with uncommitted changes.

      • Your TFS PAT can be read by the other people signed in to this server. This is a shared Remote Desktop host with other accounts signed in. While DevKit runs, any of them can open http://localhost:5850/settings and read the PAT in plain text from the page (B001, reproduced). There is no login, so they can also create or delete branches and push as you (SEC-02). And because the settings file sits in a build folder other users can modify, they can redirect the TFS URL to harvest the PAT (SEC-01).
      • A web page can do the same from outside. DevKit accepts any Host header, so a DNS-rebinding page can read the PAT and drive DevKit (B002, reproduced with a foreign Host).
      • Merge Tool can push the wrong code and still say Done. A failed checkout puts the cherry-pick on your current branch (B004, Critical, reproduced). A target branch name starting with + force-pushes a stale branch over the remote one (SEC-03, reproduced).
      • Your settings and PAT can be lost. A kill during a save empties the file, any load failure silently resets everything, and Test Connection saves a failing PAT over the working one (B113, B114, B110).

        Decisions needed before Phase 3

        1. Fast-track the exposure fixes? Your plan puts M0 (safety net) before any fix. I recommend an exception for the "Act now" items: B001, B002, SEC-01, SEC-02 (PAT and access), B004, SEC-03 (Merge Tool pushes) and B110, B113, B114 (settings loss). Each would get its own reproduction test first, as a separate commit. Approve, or keep the strict order?
        2. What should "Merged" mean? Today a work item reads Merged when every checked pull request reached the branch, even if another PR is still active or unchecked (B028). A PR that QA later reverted also counts as present when the release branch matches QA (B056). Should both become a separate state, such as "Partly checked" and "Reverted on QA", instead of Merged? Triage found two more by-design items to confirm: B024 (which branch names are protected from deletion) and B125 (PAT protection without extra entropy).
        3. Two fixes change how DevKit behaves. SEC-01 moves the settings file out of the build folder to %LOCALAPPDATA%\DevKit, migrating automatically. SEC-02 adds a launch token, so DevKit opens through a one-time link instead of a bare localhost:5850. Both change things you see. Approve, or name what must stay.
        4. Casepoint scope. Does removal include the values without the word (team code, the task catalog, tags), the employees' names, and the git history? For history: rewrite, or a fresh repository? Does your TFS process require TaskExecutionType on tasks?
